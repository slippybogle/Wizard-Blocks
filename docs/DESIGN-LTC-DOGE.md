# Design: LTC + DOGE merged mining (Wizard-Blocks-LTC)

Status: **proposal, not built.** Nothing here is merged, tagged or released.

Goal: solo-mine Litecoin (parent chain, Scrypt) with Dogecoin merge-mined
(AuxPoW) on Umbrel, for an Elphapex DG Home 1. One Stratum port; every share
is checked against both chains; fixed payout to the owner's LTC and DOGE
addresses. Same engine and repo as the BCH and BTC apps; the BCH and BTC apps
are untouched.

Facts below marked **(src)** were read from the node source code
(`litecoin-project/litecoin` master, `dogecoin/dogecoin` master). Marked
**(est)** are estimates to confirm during the work.

## 2. Litecoin specifics

**Scrypt PoW.** Block hash for PoW = `scrypt(header80, salt=header80, N=1024,
r=1, p=1, dkLen=32)`, compared little-endian against the target. The block's
*identity* hash (prev-hash links, explorers, `submitblock` result) stays
double-SHA256. Implementation: PBKDF2-HMAC-SHA256 + Salsa20/8 + ROMix (~150
lines) or `golang.org/x/crypto/scrypt` — see Question 1. Checked against
known Litecoin block vectors (genesis + recent mainnet blocks, like the BTC
vectors the repo already has).

**Share difficulty (the 65536 factor).** Scrypt Stratum uses a different
diff-1: share target = `0x0000ffff00000000…0000 / d` (2^16 easier than
Bitcoin's diff-1 `0x00000000ffff…`). So one share at Stratum difficulty `d` is
worth `d × 65536` hashes, not `d × 2^32`. Scrypt ASICs and their firmware
expect exactly this (`mining.set_difficulty 524288` means that target).
Node-reported difficulties (`getdifficulty`, `bits`) use the Bitcoin diff-1,
so: network difficulty in Stratum units = node difficulty × 65536; hashrate =
Σd × 65536 / seconds. This becomes a per-algorithm constant (`Diff1Hashes`:
2^32 for SHA-256d, 2^16 for Scrypt) used everywhere hashrate, effort, odds
and vardiff are computed.

**MWEB (src).**
- `getblocktemplate` **must** be called with `{"rules": ["mweb", "segwit"]}`,
  otherwise it errors.
- The template's `transactions` include the **HogEx** (integrating) transaction
  as the **last** entry; it is part of the merkle root like any other tx.
- The template has an `"mweb"` field: the hex of the serialized MWEB block
  (no optional-pointer prefix).
- Block serialization (`CBlock`): header, vtx, then — only if the last tx is a
  HogEx — the MWEB block as an *optional pointer*: a `0x01` presence byte
  followed by the MWEB block bytes. So `submitblock` hex = header ‖
  varint(n) ‖ coinbase ‖ template txs (HogEx last) ‖ `01` ‖ `mweb`.
- Segwit: the witness commitment (`default_witness_commitment`) goes into the
  coinbase as for BTC, with the coinbase witness reserved value.
- Payout addresses: `ltc1…`/`L…`/`M…`/`3…` only; `ltcmweb1…` (MWEB) addresses
  cannot be paid by a coinbase and are refused (the node's `validateaddress`
  plus our own check).
- To be proven on regtest: a block containing a peg-in (non-empty MWEB block)
  is accepted, and template transactions that carry MWEB data serialize
  correctly in our block (main risk item, see §7).

## 3. AuxPoW (Dogecoin, src)

- RPC: `createauxblock <doge_address>` returns `hash`, `chainid` (98 =
  `0x62`), `previousblockhash`, `coinbasevalue`, `bits`, `height`, `target`
  (**reversed byte order**). The node builds the DOGE block itself and pays
  the given address — fits fixed payout. `submitauxblock <hash> <auxpow_hex>`
  submits. (`getauxblock` is the wallet-based variant; not used.)
- **Coinbase tag (parent LTC coinbase scriptSig):** `fabe6d6d` ‖ aux merkle
  root (32 bytes, byte-reversed) ‖ merkle size (u32 LE) ‖ merkle nonce (u32 LE).
  With DOGE as the only aux chain: root = the DOGE block hash from
  `createauxblock`, size = 1, nonce = 0, so the expected slot is 0. Exactly one
  `fabe6d6d` may appear, directly before the root. ScriptSig budget (100 bytes):
  BIP34 height 4 + tag 44 + extranonce1 4 + extranonce2 4–8 + short pool tag.
- **The aux proof (`CAuxPow`)** = the parent coinbase tx (serialized **without
  witness**, since Dogecoin 1.14 has no segwit) ‖ hashBlock (32 bytes, unused,
  zero) ‖ coinbase merkle branch (the same branch sent to miners in
  `mining.notify`) ‖ nIndex = 0 ‖ chain merkle branch (empty) ‖ chain index
  (0) ‖ the 80-byte parent header.
- Dogecoin checks: coinbase is at index 0, the chain root is in the coinbase,
  merkle branch reaches the parent's merkle root, size/nonce/index match, the
  parent's chain ID is not 98 (LTC version `0x20000000` gives chain ID
  `0x2000`; version rolling cannot reach `0x0062`), and the **Scrypt hash of
  the parent header** meets the DOGE target.
- **Per share:** hash once with Scrypt, then compare against three targets:
  share (accept/reject), DOGE (submit to `submitauxblock`), LTC (submit the full
  LTC block). DOGE's difficulty is far lower than LTC's, so a DOGE block will
  happen much more often than an LTC block.

### 3b. Phase 3 decisions (checked against dogecoin v1.14.9 source)

- **Release:** Dogecoin Core v1.14.9. `SHA256SUMS.asc` good signature from
  Patrick Lodder, key `DC6EF4A8BF9F1B1E4DE1EE522D3A345B98D0DC1F` (the copy in
  the repo expired 2024-07; the keyserver copy is valid to 2028-08-01); x86_64
  tarball SHA-256 `4f227117…d4f8`. Built with ZMQ.
- **Byte-for-byte tests:** real Dogecoin **mainnet** AuxPoW blocks 371337
  (the first), 748634 and 894863 from libdohj (Apache-2.0). The last two were
  merged-mined with other chains (chain branches of 6), so the multi-chain
  tree code is tested on real data.
- **Several aux chains later:** the commitment code builds a chain merkle tree
  of any size (slot = `getExpectedIndex`, nonce searched for no clashes). With
  DOGE alone: size 1, nonce 0, root = the DOGE block hash.
- **New DOGE block:** new jobs with `clean_jobs=true` on the same LTC
  generation. Shares still arriving on the previous jobs stay valid LTC
  shares; Dogecoin itself refuses the outdated aux block ("block hash
  unknown"), so nothing stale is counted as a DOGE block.
- **A share solves DOGE whatever it means for LTC:** checked on every share,
  even one on a superseded LTC job. One solution per DOGE block is submitted.
- **Share difficulty** is capped at the lower of the LTC and DOGE network
  difficulties, so no block-solving share is withheld from either chain.
- **DOGE node down:** LTC continues without the tag; merged mining resumes on
  its own. **No DOGE address:** LTC only, logged at startup (the page says so
  in Phase 4).
- **DOGE rejections:** `submitauxblock` returns only true/false (the reason
  is written to the Dogecoin node's log, not returned over RPC). The engine
  logs the result and the full AuxPoW hex and saves it under
  `rejected-blocks/`.
- **Regtest:** Dogecoin requires AuxPoW from height 20 and mines on demand
  without peers; LTC and DOGE regtest share the target `0x207fffff`, so every
  solving share is a block on both chains.

## 4. Engine changes

- **Coin/algorithm abstraction:** `Algo` (SHA-256d | Scrypt): PoW hash
  function, `Diff1Hashes`, share-target formula. Coins: `ltc` (parent, Scrypt,
  segwit + MWEB), `doge` (aux, Scrypt, chain ID 98). Address encodings for LTC
  (bech32 `ltc`/`tltc`/`rltc`, base58 versions 0x30/0x32/0x05) and DOGE
  (base58 0x1e/0x16 mainnet, testnet/regtest variants), with test vectors.
- **Work:** the LTC template plus the current aux block go into each job: the
  coinbase gets the AuxPoW tag; the block assembler appends the MWEB block.
  Jobs remember the aux hash and target they committed to.
- **Refresh:** new LTC tip (ZMQ/poll) → new job, `clean_jobs=true`. New DOGE tip
  (DOGE ZMQ/poll, about every minute) → new aux block → new job with
  `clean_jobs=true` (old work would only produce stale DOGE blocks). Aux
  blocks are also refreshed periodically (~30 s) for fees, without clean.
- **Two node clients**, each with its own ZMQ, poll and status: the UI shows
  both. Mining runs if LTC is synced. If DOGE is down or syncing, the engine
  keeps mining LTC only (no tag) and shows DOGE as unavailable.
- **Stats per chain:** blocks found / pending / orphaned, best share as a % of
  each chain's difficulty, effort since the last block (Σd×65536 / (node
  difficulty × 2^32)), odds. Block records carry the chain.
- **Vardiff for the DG Home 1 (2.1 GH/s, 630 W):** one share per ~10 s means
  d ≈ 2.1e9 × 10 / 65536 ≈ 320,000. Start at 262,144, min 1,024, max 2^31,
  same retarget logic. `d=` in the password still pins it.
- **Stratum:** unchanged protocol. Version rolling is supported if the miner
  asks; Scrypt ASICs usually don't.

## 4b. Pool settings for owned and rented hashrate

Target hardware: Elphapex DG Home 1, firmware **DG-Home1_V1.0.5**, 2.1 GH/s.
The owner usually runs it at difficulty 200,000 (the miner's default average
is 262,144); both sit at one share every ~7–8 s.

Settings panel in the LTC app (changes apply live, no restart), so rented
hashrate (NiceHash / MiningRigRentals style) can be pointed at the pool:

- Difficulty mode: fixed, or vardiff with start / min / max and target seconds
  per share; limits high enough for rented GH/s–TH/s.
- Per-worker overrides (e.g. the DG Home at 200,000, a rental at its own value).
- Honour the miner's `d=` password and `mining.suggest_difficulty` (each can be
  switched off).
- `mining.extranonce.subscribe` acknowledged; frequent reconnects are not
  locked out; connection limits tuned for marketplace proxies.
- Live per-worker readout: current difficulty, share rate, rejects.
- Docs: router port forward to the Umbrel's Stratum port (50333) so a
  marketplace can reach it. Payout is fixed to the owner's addresses, so a
  renter cannot redirect rewards.

## 5. Testing

- **Unit:** Scrypt against vectors; LTC/DOGE address vectors; coinbase tag
  layout; AuxPoW serialization against a known-good mainnet DOGE AuxPoW block
  (parse a real one and rebuild it byte for byte); MWEB block assembly against
  a real mainnet LTC block that has an MWEB part.
- **Regtest (Docker), the gate before any release:** litecoind (with MWEB
  activated by mining past activation, plus a peg-in transaction so the MWEB
  block is not empty) and dogecoind side by side, with the engine and a CPU
  Scrypt test miner:
  1. LTC blocks accepted (with and without an MWEB part), paying the LTC address.
  2. DOGE blocks accepted via `submitauxblock`, paying the DOGE address.
  3. **A single share that is a block on both chains**, accepted by both nodes.
  4. A DOGE tip change mid-job: clean jobs, no invalid DOGE submissions.
  5. DOGE node stopped: LTC mining continues; it recovers when DOGE returns.
  6. Pruned nodes with txindex off.
- **Testnet trial:** LTC testnet4 + DOGE testnet nodes on the Umbrel (small
  chains, quick sync), the DG Home 1 pointed at the testnet port for an hour or
  two. Expect many DOGE testnet blocks and probably some LTC testnet blocks;
  check them on testnet explorers. Then mainnet.

- New app `fladnagmai-wizard-blocks-ltc` ("Wizard-Blocks-LTC"), depending on

  and DOGE node status, blocks found, best share, effort, odds; one workers
  table; blocks table with a chain column (links to LTC and DOGE explorers);
  Settings with **two payout addresses** (LTC and DOGE), both checked by their
  nodes; no work until the LTC address is set; DOGE is optional (without it,
  LTC only).
- Same image as the other apps (it is one binary); the two node images are
  separate (see Question 2).
